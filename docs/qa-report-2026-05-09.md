## A. CRITICAL ISSUES (must fix before prod)

### A1. Variants editor will 500 when deleting a variant that has any historical sale
**File:** `app/api/admin/products/[id]/route.ts` (PATCH variants block) + new `components/admin/ProductVariantsEditor.tsx`
**Root cause:** Schema FKs to `productVariants.id` from historical/audit tables (`orderItems`, `shipmentItems`, `returnItems`, `invoiceItems`, `paymentEntries.variantId`, `purchaseOrderItems.variantId`) intentionally omit `onDelete: cascade` — DB raises FK violation. The PATCH route does a hard `db.delete(productVariants)` for ids dropped from the incoming list.
**Repro:** Edit any product that has been ordered, remove a variant row, click Save → backend throws `update or delete on table "product_variants" violates foreign key constraint`.
**Fix:** Soft-delete via `productVariants.isActive = false` (column exists at `db/schema.ts:435`). Hide inactive ones from storefront resolvers; keep them in admin to maintain referential integrity.

### A2. Inconsistent product-images editors live side-by-side
**Files:** `app/admin/(protected)/products/[id]/images/page.tsx` (uses **old** `components/admin/ProductImagesEditor.tsx`) vs the inline `ProductImages` in `ProductEditTabs.tsx` (new).
**Effect:** The dedicated `/products/[id]/images` URL has no reorder, no set-primary, no alt-edit. Two routes manage the same data with different capabilities — confusing and a regression risk.
**Fix:** Delete the standalone images page + legacy component. Inline panel covers the use case.

### A3. school_admin can browse but cannot save edits
**Files:** `app/admin/(protected)/products/page.tsx` (allows `school_admin`) vs all PATCH/POST/DELETE routes under `app/api/admin/products/**` (require `super`).
**Effect:** A school_admin sees products in the list, opens one, hits Save → 401/403. UX dead-end.
**Fix:** Restrict the admin product list and edit pages to super/ops only.

### A4. Build pipeline not verified end-to-end
**Cause:** `npm run build` timed out in the QA sandbox. The Dockerfile change (esbuild→migrate.js) and the entrypoint switch from `node server.js` to `/app/start.sh` were not exercised.
**Risk:** First production deploy could fail at container start.
**Fix:** Run `docker build && docker run` locally before merging.

# Round 3 — Deep QA pass (post-soft-delete second-order effects)

After landing the round-2 fixes, a second deep ultrathink pass was run to find downstream / second-order issues introduced by the soft-delete model.

## Critical second-order issues found

### R1. Variants-page resurrection loop (CRITICAL)
**File:** `app/admin/(protected)/products/[id]/variants/page.tsx`
**Cause:** Loader fetched ALL variants regardless of `isActive`. Editor sent that full list back on save. Server PATCH set `isActive=true` for every incoming row → previously-deactivated rows came back to life on every Save.
**Fix:** Loader filters `isActive = true`.
**Impact:** Without this, soft-delete was effectively unusable from the UI.

### R2. Cart-checkout could ship a soft-deleted variant (HIGH)
**File:** `lib/repos/cart.ts:readCart`
**Cause:** `readCart` queries `productVariants` with no `isActive` filter; a variant deactivated between "added to cart" and "checkout" remained in the snapshot, billed normally, and decremented stock.
**Fix:** Filter `isActive = true` in the variants fetch. Lines silently disappear from the snapshot.

### R3. Public size→variantId lookup leaked inactive (HIGH)
**File:** `app/api/shop/variant/route.ts`
**Cause:** Public endpoint used by the storefront PDP buy box. Could return an inactive variantId that subsequently flows into add-to-cart.
**Fix:** Filter `isActive = true`.

### R4. AdminShell bounce loop for school_admin (MEDIUM)
**Files:** `components/admin/AdminShell.tsx`, all 5 product pages
**Cause:** Round-2 restricted product pages to super/ops + redirected to `/admin/login` on guard fail. But school_admin sessions are still valid; nav still showed Products link → click → redirect to login → already authenticated → confusing.
**Fix:** (a) `NavItem` now supports `roles?: ("super"|"ops"|"school_admin")[]`; Catalog group items hidden for school_admin. Empty groups don't render. (b) All 5 product page redirects switched from `/admin/login` to `/admin/dashboard` so authenticated-but-wrong-role lands somewhere they can use.

### R5. Image PATCH was not transactional (MEDIUM)
**File:** `app/api/admin/products/[id]/images/[imageId]/route.ts`
**Cause:** When `isPrimary=true`, route demoted siblings then updated target — two separate writes. Concurrent delete/disconnect between them = no primary image.
**Fix:** Wrapped both statements in `db.transaction(async tx => {...})`.

### R6. Variant counts in admin list/edit included soft-deleted (MEDIUM)
**Files:** `app/admin/(protected)/products/page.tsx`, `app/admin/(protected)/products/[id]/page.tsx`
**Fix:** Both `COUNT(*)` queries now filter `isActive = true`. Header subhead and list column now report active count.

### R7. variant-resolver had no defensive isActive filter (LOW)
**File:** `lib/repos/variant-resolver.ts`
**Cause:** Although list/PDP callers were fixed in round 1, any future caller (e.g. admin export, ERP sync) could pass mixed IDs. Belt-and-suspenders fix.
**Fix:** Filter `isActive = true` inside `resolveVariants`.

### R8. low-stock + auto-PO included inactive SKUs (MEDIUM/operational)
**Files:** `lib/auto-po.ts:lowRows`, `lib/repos/inventory.ts:listLowStock`
**Cause:** Auto-PO scheduler would create POs for retired SKUs; low-stock report would alert ops about discontinued items.
**Fix:** Both queries now filter `productVariants.isActive = true`.

# Round 4 — Continued ultrathink (deployment + edge UX)

## Critical issues found

### R9. BuyBox crash if all variants are inactive (HIGH)
**File:** `components/shop/pdp/BuyBox.tsx`
**Cause:** `const [size, setSize] = useState(product.sizes[0])` returns `undefined` when the storefront filter (round 1+3 fix) drops every variant. `add(product, undefined)` then poisons the cart with `undefined` size keys.
**Fix:** Default `size` to `""`; compute `noSizesAvailable = product.sizes.length === 0` and `canAdd = !noSizesAvailable && size && product.inStock`. `handleAdd` early-returns if `!canAdd`. Visible amber notice shown when no sizes.

### R13. Migrator silently skipped 4 of 6 SQL files (CRITICAL — deployment-breaking)
**Files:** `db/migrate.ts`, `db/migrations/meta/_journal.json`, `Dockerfile`, `scripts/start.sh`
**Root cause:** `db/migrations/meta/_journal.json` only registers 0000 and 0001. Files 0002–0005 were created by hand (not via `drizzle-kit generate`), so the drizzle-orm migrator (`drizzle-orm/postgres-js/migrator`) — which iterates the journal — would silently skip them. On a fresh deploy:
  - 0000, 0001 applied ✅
  - 0002 (numbering counters), 0003 (purchase invoices), 0004 (loyalty + gift cards), 0005 (school color map) NEVER applied ❌
  - Container starts, DB is half-built, runtime queries fail with "relation does not exist".
**Why it didn't bite during dev:** Dev workflow uses `db:up` + `db:push` (drizzle-kit's diff-and-apply), which doesn't read the journal. Production deploys would have failed silently.
**Fix:** Replaced `db/migrate.ts` with a file-based migrator:
  1. Creates `__schema_migrations(filename, applied_at)` tracking table.
  2. **Bootstrap pass**: for each file in a fingerprint map, if all canonical tables it creates already exist (e.g., `parents`/`products`/`orders` for 0000), record the file as applied without running it. Handles existing DBs that were migrated by hand or via drizzle-kit.
  3. Reads every `*.sql` file lexicographically and runs ones not yet recorded, each in its own transaction.
  4. Records applied files atomically with execution.
  Dockerfile esbuild now has only `postgres` as external; drizzle-orm dependency removed from migrator. Single COPY of `node_modules/postgres` into runner.

## Behaviour matrix — migrator on common scenarios

| Scenario | Behaviour |
|---|---|
| Fresh empty DB | Bootstrap finds no fingerprint tables; runs all 6 migrations in order; records all. |
| Existing prod DB (0000–0004 applied via psql/drizzle-kit) | Bootstrap detects fingerprint tables for 0000–0004; marks them applied; runs only 0005. |
| Container restart after successful migrate | Tracking table shows all applied; pending=0; logs "up to date". |
| Migration 0005 fails mid-execution | Transaction rolls back; tracking row not inserted; container exits non-zero (with `MIGRATIONS_REQUIRED=1`). Re-deploy after fix re-runs 0005 cleanly. |
| Hand-applied migration file added later (0006_…) | Bootstrap doesn't recognize it (no fingerprint); runs it like any pending file. Add fingerprint entry only if you also expect existing DBs to skip it. |
