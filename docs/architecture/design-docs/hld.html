01

Introduction

1.1 Purpose

This High-Level Design (HLD) records the architecture of Inventre as it runs in production on 23 September 2026. It is the reference for onboarding engineers, for change impact assessment, for audits, and for planning the next phase of the platform. It is written from the source code and the live deployment, not from earlier plans, so where a plan and the running system disagree, this document follows the running system.

1.2 Scope

In scope

  • Inventre storefront (inventre.in) and its public pages
  • Inventre admin back office (/admin)
  • Fee ledger console (/fees) and its MyClassBoard import
  • Parent concern portal (/portal) and support view-as-parent
  • Backend API, database, cache, media storage, background jobs
  • Integrations with the Audit ERP, ERPNext, CCAvenue, SMS gateway, e-mail, MyClassBoard
  • Deployment topology on the production host and the dev/test environments

Out of scope

  • Internal design of the Audit ERP (separate FastAPI system, separate repository and host)
  • Employee Rewards Marketplace and Task Manager (separate applications that share the host only)
  • Procurement application (third-party system)
  • Business processes at schools and the warehouse

1.3 Audience

Engineering, DevOps, QA, product management and external auditors. Section 3 to 7 assume familiarity with web architecture; Section 2 is readable by non-engineers.

1.4 Conventions

  • Paths such as app/api/cart are relative to the repository root /root/Inventre.
  • "Audit ERP" means the in-house fulfilment ERP at audit.inventre.online; "ERPNext" means the legacy ERP at erp.inventre.in.
  • Money values inside the system are stored in paise (integer); the UI renders rupees.
  • Status pills: Live in production, Partial built but limited, Gap missing or defective, Planned.

02

System overview

Inventre is an e-commerce platform for school uniforms, books and kits. A parent signs in with their mobile number, sees only the catalogue for their child's school and grade, builds an order (often a pre-configured "Magic Box" kit), and pays through CCAvenue. Inventre's own Postgres database is the system of record for the storefront; a bridge keeps the fulfilment ERP in sync and pulls delivery status back.

03

Architecture

3.1 Architectural style

Inventre is a modular monolith: one Next.js 15 application serves the storefront, the admin console, the fee console, the public portal and the entire HTTP API from a single deployable container. Business logic lives in a server-only layer (server/) that both the API route handlers and the server-rendered pages call. Long-running or scheduled work is not a separate worker process; it is exposed as authenticated /api/cron/* endpoints that the host's cron daemon calls. This keeps deployment simple (one image, one container) at the cost of coupling the job runtime to the web runtime.

3.5 Rendering model

The two halves of the application render differently, and that is intentional but worth knowing:

  • Storefront pages are client components. /shop, the product page, cart, checkout and orders are marked "use client" and fetch JSON from /api/* with cache: "no-store". A focus-refetch hook refreshes data when the tab regains focus. Exception: the exchange and missing pages are server components that read the database directly.
  • Admin pages are server components. 104 of 122 protected pages import the database or server layer directly and render on the server; writes go through /api/admin/* (only four server actions exist).
  • Everything is dynamic. About 115 pages export dynamic = "force-dynamic"; there is no ISR or tag revalidation. Cache-Control headers make /shop/* private, no-store and the home page publicly cacheable for 60 s.

Data architecture

One PostgreSQL 16 database (inventre) is the system of record. Redis holds only ephemeral data. Media binaries live in Cloudflare R2 with metadata rows in Postgres.

5.1 Domain map

Figure 3 — Table families. Bold headings are domains; the full column-level model is in the LLD, Section 5.

5.2 Principles in force

  • Money in paise. All amounts are integer paise; exports label units explicitly.
  • Snapshots at order time. Order items snapshot name, price, tax, size and colour so later catalogue edits do not rewrite history.
  • Soft state through enums. 34 Postgres enums (order_status, payment_status, return_status, …) constrain lifecycle columns.
  • Canonical grade. students.grade is the single source for a student's grade; the ERP receives it verbatim (see LLD 5.4 for the +3 legacy offset trap).
  • Append-only trails. activity_log (admin actions), stock_ledger, otp_logs, storefront_events are never updated in place.
  • Migrations are the only schema path. 92 SQL files; the container runs the migrator before next start. Verified on 2026-09-10 to rebuild an empty database to 94 tables / 1,100 columns.

5.4 Backup and recovery

  • Point-in-time: WAL streamed continuously to /root/backups-archive/wal (systemd inventre-wal-stream, slot inventre_wal) + full base backup 00:00 IST → restore to any second within 30 days.
  • Logical: nightly dump 00:10 IST (scripts/backup-db.sh, 14 daily + monthly); 6-hourly snapshot (dump, AES-256 env, MinIO volume); .env.deploy also mirrored on its own, re-encrypted within 5 min of a change.
  • Code: on every commit (git hook), after every deploy and at 00:20: bundle of all branches to the mirror and push to GitHub Sunith0801/Inventre-Website; uncommitted edits packed every 5 min.
  • Off-host, encrypted: rclone every 5 min to Microsoft 365 (SharePoint) through a crypt layer; failure and staleness e-mails; weekly automatic restore test with e-mail. Recovery kit in the same folder: RESTORE/bootstrap-new-server.sh rebuilds a fresh server from the folder plus one passphrase (docs/runbooks/restore-from-m365.md); manual fallback docs/runbooks/host-rebuild.md.
  • Restore of a production dump was verified on 2026-09-10 (refactor baseline).
  • A streaming relay replica design exists (staging.inventre.in writable clone via inventre-relay-postgres) and a Redis Sentinel guide is in deploy/replicas.
  • Live Off-host copies land in the company Microsoft 365 tenant every 5 minutes, encrypted before upload (F-11, 2026-09-23).

Integration principle

Figure 4 — Production deployment. All Inventre services are Docker containers in the inventre-deploy compose project; nginx and cron run on the host.

7.3 Build and release

  1. Preflight (scripts/deploy.sh): refuses uncommitted source changes unless --allow-dirty; runs npm run typecheck and npm test unless --skip-verify.
  2. Build on the host with a warm .next/cache (~90 s for code-only changes; 3–4 min cold). The Dockerfile is a three-stage build (deps → builder → runner) producing a standalone bundle plus a compiled db/migrate.js.
  3. Release: --fast copies the build into the live container and restarts; full mode recreates the container with docker compose -p inventre-deploy --env-file .env.deploy up -d --no-deps app. The previous image is tagged inventre-app:rollback-* for one-command rollback.
  4. Boot: the container runs the migrator, then next start; Docker healthcheck hits /api/health (DB + Redis ping).
  5. Verify: verify-deployment.sh asserts the live /api/version reports the build id and the commit just built (gitSha, gitBranch, dirty, builtAt are baked into the bundle by next.config.mjs), all six security headers, and the admin and shop doors; a failure rolls back to the snapshot automatically.
  6. Post-deploy: open admin and fee tabs detect the new BUILD_ID through /api/version and reload themselves (or prompt when a form is dirty).
Deployment trap — builds from the working tree (F-01, closed 2026-09-23)

The build context is the working directory of /root/Inventre, not a git revision, and on 2026-09-10 a deploy from another checkout replaced production twice. Three layers now close this: every other checkout has its compose file renamed and a refusal guard in deploy.sh; every build carries its commit, branch and dirty flag in /api/version and verify-deployment.sh fails a deploy whose live commit is not the one just built; the 10-minute monitor logs a foreign commit (one not in this checkout's history) as well as a lost security posture.

8.2 Defence layers

Edge and transport

  • TLS via Let's Encrypt; HSTS, X-Frame-Options DENY, Permissions-Policy, enforcing CSP for frame-ancestors/object-src/base-uri, full CSP in report-only
  • nginx body caps (12 MB; 60 MB for return photo upload); middleware excludes multipart routes from the 10 MB edge body limit
  • Key-only SSH, fail2ban, firewall on Docker-published ports (firewall-docker-ports.sh)

Application

  • Middleware verifies JWT signatures at the edge before any handler runs
  • CSRF: SameSite=Lax cookies plus Origin/Referer same-host check on all state-changing JSON APIs (webhooks and the CCAvenue callback are excluded and use signatures / AES instead)
  • zod validation on every body and query; apiHandler converts exceptions to JSON, never HTML stack traces
  • Redis-backed rate limiting on OTP and login
  • All 12 cron endpoints authenticate through one helper, server/cron-auth.ts (Authorization: Bearer CRON_TOKEN, constant-time compare); an architecture test fails the build if a route bypasses it

Data

  • bcrypt password hashes; OTP codes only in Redis with TTL
  • Order detail and exchange pages scoped to the requesting family graph (co-guardians 404 outside it)
  • Staff names stripped from tracking timelines server-side
  • Redis password-protected (2026-09-10); Postgres reachable only on the host

Audit and detection

  • activity_log records every admin mutation with before/after
  • otp_logs, storefront_events (5xx), communications
  • Static analysis run stored in docs/security/SAST-20260909
  • Production monitor detects header/authorization regressions every 10 min; gsocket and ssh-it watchdogs after the June 2026 compromise

8.3 Known security gaps

  • Fixed Admin section gating is now complete. All 39 sections under app/admin/(protected) carry a SectionGate layout, 141 admin API routes call requirePermission, and tests/architecture/invariants.test.ts fails the build if either regresses (verified 2026-09-23; F-02).
  • Fixed Cron authentication unified on 2026-09-23: one token, one header, constant-time compare, token rotated (F-17).
  • Fixed Secrets consolidated on 2026-09-23: cron files, the compose file, the deploy script and the MCB import scripts no longer contain any credential; everything is read from .env.deploy (mode 640, owner root, read ACL for the backup user). Stray .env.*.bak copies moved to a root-only archive (F-03).
  • Partial Credential rotation after the June–July 2026 root compromise: every secret that lives only on this host was rotated on 2026-09-23 (JWT with a 7-day dual-key grace window, AUTH, support-view, Redis, MinIO, Grafana, OTP bypass, cron token). The Postgres password is rotated by scripts/rotate-db-password.sh; secrets shared with partners still need a coordinated change (F-04).
  • Partial /api/downloads in the Rewards application grants any private file to any entity admin; not Inventre, but shares the host (tracked there).

Assumptions, constraints & risks

10.1 Assumptions

  • Inventre's Postgres remains the storefront system of record; the Audit ERP is the fulfilment system of record. Neither replaces the other.
  • Parents identify by mobile number; a phone may belong to several guardians and several students (family graph), never assumed one-to-one.
  • Catalogue eligibility is decided server-side from the student's school and grade; the client only renders what it is given.
  • The single production host has enough headroom for the season peak with caching; horizontal scaling is a future option, not a present need.

10.2 Constraints

  • One host runs production, two test environments and two unrelated applications; port and container-name collisions are a real hazard (never pkill next-server broadly).
  • Production database reads are permitted for analysis; writes to production data are performed by the owner, not by tooling.
  • Prod builds from the working tree; branch main may lag what is deployed.
  • ERPNext is unreachable from the production host by firewall; only the Audit ERP is a live partner.

Glossary & references

12.1 Glossary

Audit ERP
In-house fulfilment and call-centre ERP (FastAPI + Postgres) on 217.216.58.218, referred to as "audit" in code and logs.
Magic Box
A configurable bundle (uniform + books + accessories) sold as one product; one per student; components chosen in the configurator and stored as bundle_selections.
Bookkit
A fixed book bundle per school and grade; Grade 11–12 kits carry Mandate × Core × Elective subject variants and 2nd/3rd language variants.
Ground Stock
Physically counted stock per SKU maintained in the Audit ERP; bridged into Inventre bins every 5 minutes.
RTN / MIS / CON
Exchange request, missing-item claim, concern ticket. Numbers minted by the Audit ERP (RTN-M-, MIS-M-) or Inventre (RTN-YYYY, CON-).
MCB
MyClassBoard, the school management system that holds student rosters, fee schedules and receipts for 13 branches.
Packing state
Per-item fulfilment state from the ERP used to gate exchange/missing buttons and to badge order lines.
Support view
Read-only impersonation session an Audit agent uses to see a parent's storefront.
IELP / IESP
Parcel codes: LARGE parcel (bookkits) and SMALL parcel (uniforms); one order may split into both.
