01

Summary and commitments

Inventre runs on one server. Until this month, losing it would have meant losing up to 6 hours of orders and the entire code history since June. As of 23 September 2026 the database is streamed off the server continuously, the code is pushed to GitHub on every commit, and everything needed to rebuild lives, encrypted, in the company's Microsoft 365 alongside a one-command recovery kit. What remains is to agree the targets below, name the people, and rehearse.

Commitments (approved by the owner on 2026-09-24)

MeasureTargetWhat it means
RPO (Recovery Point Objective): most data we may lose5 minutesAfter a total loss, orders placed more than 5 minutes before the failure are recovered. Achieved by continuous transaction-log streaming plus a 5-minute off-host sync.
RTO (Recovery Time Objective): longest acceptable downtime4 hours business hours
Next morning overnight		The technical rebuild is 60 to 90 minutes; the rest is people, DNS and partner steps. Overnight incidents (outside 07:00 to 21:00 IST) are recovered by 09:00.
Availability during the ordering season (May to August)99.5 % in business hoursAbout 1 hour of unplanned downtime per month in business hours.
Maximum tolerable outage before the business is materially hurt2 business daysBeyond this, schools escalate, parents lose trust and delivery slots are missed. Every playbook is designed to finish far inside it.
Drill frequencyQuarterly restore drill, annual full rebuildA backup that has never been restored is a hope, not a backup.
Current measured position

RPO: about 5 minutes (verified: transaction-log segments and the 5-minute mirror are live). RTO for a full rebuild (Scenario A): 5 minutes 19 seconds technical time, measured on 2026-09-24 on a clean Ubuntu 24.04 machine with nothing but the RESTORE folder and one passphrase (fetch, code, point-in-time database, build, verified start). The manual tail (DNS, nginx, certificate, cron, mail) is estimated at 20 minutes on top. The point-in-time restore alone (Scenario B) took 45 seconds. Both numbers are in the drill record (Section 9).

What the targets do not cover

A failure at CCAvenue, the Audit ERP or the schools' own systems is outside Inventre's control; the fallbacks in Section 2.2 limit the damage but the recovery clock belongs to the partner. A deliberate attack that also destroys the Microsoft 365 backups would need the tenant's own recycle-bin and retention protections; enabling retention locks on the backup library is action D-06.

Scenarios and playbooks

Each playbook starts the same way: declare, snapshot, then act. Nothing is rebooted, deleted or redeployed until the technical lead has written the first timeline line and, where the host is alive, taken a snapshot.

Scenario A — The server is lost (hardware, provider, ransomware, fire)

StepActionWhoTime
A1Declare the incident; put the maintenance notice up if any part of the old host still answers; send the first message (Section 7, template 1).Owner, comms0:00–0:15
A2Order a new Ubuntu server (4 vCPU, 16 GB, 200 GB) from the provider; note its IP.Owner0:15–0:30
A3Download the RESTORE folder from SharePoint, copy it to the new server, run bash bootstrap-new-server.sh, enter the recovery-kit passphrase. It fetches, restores code and configuration, replays the database to the last received segment and starts the app.Technical lead0:30–1:45
A4Check the counts the script prints (tables, orders, students, newest order time). If the newest order is older than expected, stop and investigate before opening to parents.Technical lead1:45–1:55
A5nginx + certificate, DNS A records to the new IP, cron files, WAL streaming service, mail relay, CCAvenue SFTP user. Rename the SharePoint prod folder to prod-old-<date> before the first sync from the new host.Technical lead1:55–2:30
A6Verify: health endpoint, security headers, a test login, a test order to the CCAvenue test page, the ERP drain log shows sent. Tell CCAvenue and the ERP team the new outbound IP if they allow-list.Technical lead2:30–3:00
A7Send the all-clear (template 3). Within two weeks: post-incident review, this document updated.Comms, owner3:00

RPO: about 5 minutes. RTO: technical part measured at 5 min 19 s on a clean machine (2026-09-24) plus about 20 minutes of manual tail; 3 hours including people time remains the commitment. Reference: docs/runbooks/restore-from-m365.md.

Scenario B — Bad data: a faulty deploy, a wrong bulk import, a deleted table

StepActionWhoTime
B1Stop the bleeding: roll the application back to the previous image tag (docker tag … rollback-*, redeploy, 1 minute) if a deploy caused it; disable the offending cron or import if a job caused it.Technical lead0:00–0:10
B2Decide the scope with the owner: a few rows (fix forward with a script), a table (restore that table from the last dump into a scratch database and copy back), or everything since a time (point-in-time restore).Owner + technical lead0:10–0:30
B3For point-in-time: the maintenance page goes up (orders placed during the window would be lost), the technical lead runs restore-from-m365.sh restore-pitr "YYYY-MM-DD HH:MM" on the same host into a fresh data volume, verifies counts, then switches the compose stack to it. Orders placed between the target time and the restore are re-entered from CCAvenue's records.Technical lead0:30–1:30
B4Verify, reopen, all-clear; record what was lost and re-entered.Comms1:30

Drill: scripts/backup/pitr-drill.sh ["YYYY-MM-DD HH:MM:SS"] rehearses step B3 without touching the live stack. It restores from the local archive (/root/backups-archive, which holds the WAL segments the replay needs) into a throwaway container and data volume on the production host (PG_VOLUME override), prints the counts, then removes them. First run 2026-09-24 (Section 9). The dev database cannot be used for this: it has no WAL archive.

Scenario E — Key people unavailable

The deputy in Section 4 takes the role. Everything a deputy needs is in the password manager and SharePoint, not on any one laptop. If the technical lead is unavailable, the recovery kit's README is written so that any competent engineer, or an AI assistant given the folder and the passphrase, can complete Scenario A.

Templates (adapt, do not improvise)

  1. Initial: "Inventre's online store is temporarily unavailable. Your orders and payments are safe. We are restoring service and expect to be back by [time]. Payments already made will show correctly once we are back."
  2. Update: "Update [time]: restoration is under way; the store will reopen by [new time]. If you paid and do not see your order after we reopen, it will appear within an hour; no action is needed."
  3. All-clear: "The store is back online. Orders placed before [time] are intact. If you paid between [time] and [time] and your order is missing, reply to this message or call the school coordinator; we will complete it for you."
  4. Payment partner outage: "Online payment is currently unavailable due to an issue at our payment provider. You can complete your order later; your cart is saved. Urgent orders can be placed through the school coordinator."
Maintenance page

Already built: nginx serves a branded page with a 503 status when $maint_on is 1; admin and API paths stay live; staff bypass with a token. Copy the current page to nginx with /root/maintenance/sync.sh. One command: bash scripts/maintenance.sh on|off|status (backs up the nginx site file, edits the map, tests, reloads, restores on failure). Runbook docs/runbooks/maintenance-page.md; exact nginx steps in the HLD (maintenance page and nginx 503 gate).

08

Degraded operation: keeping the business going

SituationHow the business continues while systems are restored
Storefront down in an ordering windowSchool coordinator collects orders on paper or a shared sheet (child name, enrolment, items, sizes); staff key them in as offline orders when the store is back (the manual offline-order script exists) and reconcile payment separately.
Payments downAccept pay-at-school or bank transfer for urgent orders; record as offline payments; the settlement reconcile heals gateway orders later.
Fulfilment link downWarehouse works from the admin console's order list or an Excel export until the queue drains.
Login (OTP) downPassword login; supervised OTP bypass; call centre places orders on behalf of parents using view-as-parent is read-only, so orders are keyed as offline orders instead.
Fee console downFee desk works directly in MyClassBoard; Inventre's console is a reporting layer.
Engineering unavailableDeputy follows the recovery kit README; the hosting provider's console can reboot the machine; the maintenance page can be toggled by anyone with SSH (bash scripts/maintenance.sh on|off).
