01

Introduction

1.1 Purpose and scope

This Low-Level Design (LLD) explains how each part of Inventre is built so that an engineer can change it safely. It covers the repository at /root/Inventre: the Next.js application (frontend and backend in one codebase), its database schema and migrations, its integration adapters, and the operational scripts that run it. It does not cover the Audit ERP's internals.

1.2 Relationship to the HLD

The HLD fixes the boundaries: one modular monolith, Postgres as system of record, adapters for every external system, cron-driven jobs. This LLD stays inside those boundaries and names the files, functions, tables, cookies, environment variables and commands that implement them.

1.3 Conventions

  • Paths are repository-relative. server/ is the server-only domain layer; lib/ holds code shared by client and server; app/ is the Next.js App Router tree.
  • A "route" is a route.ts handler under app/api; a "page" is a page.tsx.
  • Money is integer paise; timestamps are timestamptz; IDs are UUID v4 unless noted.
  • Status pills as in the HLD: Live Partial Gap Planned.
How to use this document

Sections 2 to 6 are reference material (where things are, how they are shaped). Section 7 walks the five flows that matter most. Sections 8 to 12 are operational. Section 13 lists the traps that have bitten in production; read it before touching pricing, grades, migrations or deploys.

3.2 Layout and rendering rules

  • Root layout loads Plus Jakarta Sans (--font-jakarta), sets bg-cream text-ink-900, mounts SupportViewBanner (server half reads DB, client half counts down) and AuthGate, which logs the parent out when they leave /shop/*.
  • Dynamic by default. ~115 pages export dynamic = "force-dynamic". No ISR, unstable_cache or revalidateTag. Headers: /shop/* private no-store; /_next/static immutable.
  • Server actions exist in four files only (catalog/build, delivery-fee-rules, mcb, discounts), each followed by revalidatePath. Every other write goes through /api. Server actions break open tabs on deploy, which is why VersionWatcher exists.
  • Streaming is limited to the admin loading.tsx skeleton and three Suspense wrappers around useSearchParams. Error boundaries: app/error.tsx, app/not-found.tsx, app/shop/error.tsx (brand styling, retry + back to store; F-15).

04

Backend API design

4.1 Handler conventions

  • Shape: every handler is a Next.js route handler exporting GET/POST/PATCH/DELETE. Bodies and queries are validated with zod (142 route files) through server/api-handler.ts parseJson / parseQuery (parseBody in server/parse-body.ts is an alias). One 400 payload everywhere: {error: "<messages joined>", details: [{path, message}], issues: ZodIssue[]} (F-18).
  • Errors: {error: string} with the HTTP status; successes commonly {ok: true, …}. Middleware returns {error: "Unauthorized"} 401, {error: "Forbidden (CSRF)"} 403, and a read-only 403 in support view. failJson (5 parent routes) also records the failure in storefront_events.
  • Guards: first statement of the handler. Parent: requireParent(). Admin: requirePermission("<slug>.read|write") (141 routes), requireAnyPermission (3), requireAnyWritePermission (upload), legacy requireAdmin (2). Fees: getFeesViewer(). Cron: requireCron(req) then acquireCronLock(name, ttl) from server/cron-auth.ts (see 9.2). Service: SUPPORT_VIEW_SERVICE_TOKEN, SYNC_STAGING_KEY.
  • Side effects after writes: logActivity (14 admin routes), cache invalidation (invalidateCatalog), enqueueOrderEvent, notifications through server/notify/event-bus.ts.
  • Relative redirects: route handlers behind nginx must return a relative Location because req.url is 0.0.0.0:3000.

4.3 Representative handler

// app/api/cart/route.ts (shape, abbreviated)
export async function POST(req: Request) {
  const parent = await requireParent();                 // 401 if no inv_session
  const body = await parseJson(req, AddSchema);         // zod → 400 {error, details}
  if (body instanceof NextResponse) return body;
  const student = await assertStudentOfParent(parent.id, body.studentId);
  await assertGradeEligible(student, body.variantId);   // server/grade-filter.ts
  const lines = body.bundleId
    ? await expandBundle({ bundleId: body.bundleId, choices: body.bundleSelections })
    : [{ variantId: body.variantId, qty: capToOne(body.qty) }];
  await assertHouseColourLock(student, lines);          // 409 on mismatch
  const cart = await cartRepo.addLines(parent.id, student.id, lines);
  return NextResponse.json({ ok: true, cart });
}

9.3 Design rules for a cron endpoint

  1. First statement: const denied = requireCron(req); if (denied) return denied; (server/cron-auth.ts: Authorization: Bearer CRON_TOKEN, constant-time; 503 when unset, 401 when wrong). The architecture test fails the build if a cron route skips it or reads a retired CRON_SECRET / CRON_KEY.
  2. Second statement: const lock = await acquireCronLock("<job>", ttlSeconds); if (!lock) return cronLockedResponse("<job>"); and the body in try … finally { await lock.release(); }. Redis SET NX PX with a random token, released by compare-and-delete; TTL = the cron line's curl timeout. If Redis is unreachable the job runs unlocked (one instance today; every job is idempotent or uses FOR UPDATE SKIP LOCKED). Verified: two simultaneous erp-poll calls, one answered {skipped: "locked"}.
  3. Bound the work per tick (chunk size, max lookups) so a tick finishes inside the curl timeout (25–240 s).
  4. Return a JSON summary ({processed, failed, skipped}) that the cron log captures; never 200 on a silent failure.
  5. Log to /var/log/inventre-<job>.log via the cron line; long-term, expose a heartbeat metric (F-13).

10.3 Rotation procedure

  1. Copy .env.deploy to /root/.secrets-archive/ (0700).
  2. JWT: move the current value to JWT_SECRET_PREVIOUS, generate a new JWT_SECRET; delete the previous after 7 days. PORTAL_TOKEN_SECRET and GIFT_CARD_SECRET must stay pinned to the secrets their tokens and codes were issued with.
  3. App-only secrets (AUTH_SECRET, SUPPORT_VIEW_JWT_SECRET, OTP_BYPASS_CODE, CRON_TOKEN): change the value, run ./scripts/deploy.sh (full mode re-reads .env.deploy). The cron file sources the same file, so cron follows automatically.
  4. Redis / MinIO: change the value, deploy the app, then stop + remove the old container and docker-compose … up -d --no-deps redis. Never --force-recreate with compose v1 (F-22).
  5. Postgres: scripts/rotate-db-password.sh (ALTER ROLE → .env.deploy → recreate pgbouncer + app → fast deploy → verify).
  6. Shared secrets (ERP webhook/poll, support-view service token, CCAvenue, R2, SMTP, SMS, MCB): agree a window with the other party, change both sides, verify the integration's next tick.
Secret handling rules

Never print or commit values. .env.deploy is the single place production secrets live (cron files, compose, scripts all read from it); environment dumps in chat or logs leak them. Retired env backups are in /root/.secrets-archive (0700). Open item: rotation of DB, Redis, JWT and gateway keys after the 2026 compromise (F-04).

11.1 Error-handling conventions

  • Route handlers return JSON errors with the right status; never HTML. Validation 400, auth 401, permission or CSRF 403, not-found 404, conflict 409 (house colour, duplicate request), gateway 502 for partner failures.
  • Telemetry must never break the customer: onRequestError swallows its own failures.
  • Parent-facing network failures are translated by errorMessageFor into plain language.
  • Guards that hide data return 404, not 403, when the requester is outside the family graph.

12.4 Production deploy

cd /root/Inventre                     # the ONLY deploy source
git status --porcelain                # must be clean (or --allow-dirty with a reason)
docker tag inventre-app:latest inventre-app:rollback-<topic>-$(date +%Y%m%d)
./scripts/deploy.sh --fast            # code-only: build → docker cp → restart

./scripts/verify-deployment.sh        # health, headers, build id AND commit (run automatically by deploy.sh)
tail -f db_backups/production-monitor.log

deploy.sh exports the commit, branch and dirty flag so the bundle can report them; with --allow-dirty the live site reports dirty:true, which is visible in the monitor log. If compose must be run by hand: docker compose -p inventre-deploy -f docker-compose.deploy.yml --env-file .env.deploy up -d --no-deps app. Never use deploy/release.sh (legacy PM2 path with drizzle push).

12.5 Rollback

docker tag inventre-app:rollback-<topic>-<date> inventre-app:latest
docker compose -p inventre-deploy -f docker-compose.deploy.yml --env-file .env.deploy up -d --no-deps app
# or, for a --fast deploy: scripts/restore-snapshot.sh (restores /app/.next.prev)

Migrations are forward-only; a rollback that needs schema reversal requires a new down-migration written by hand.

12.6 Audit ERP side (for cross-system changes)

Separate repository and host; deploy by rebuilding its Docker image over SSH. Its dev checkout is untracked, older and diverged — never copy dev → prod there. Frontend overlays by the audit team can clobber changes within the hour; verify the served index-*.js hash after deploying.
